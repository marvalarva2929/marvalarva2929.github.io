Running an LLM at 1.5 tokens/s on a chip with 32 KB of memory

    TL;DR, intro and motivation

    This article describes my work at Longhorn Silicon, a student-led silicon design organization at UT Austin, during its first tapeout. I've always been interested in low-level performance software and kept up with LLM architectures, but I had never done real inference work. Longhorn Silicon is the beginning of my work in this growing and important field.

    Throughout the semester I built specialized kernels for GPT-Neo (TinyStories-28M) to run on our chip. Using these kernels, we've reached around 1.4 tokens/second on a chip with 32 KiB of SRAM. Below I explain in depth how I built these kernels to reach that performance, the challenges and problems we faced along the way, how I communicated and co-designed with our hardware teams, and what we plan to do next.

    Biggest accomplishments so far:

    • Flash attention. I implemented attention so it streams the KV cache through the chip one block at a time, which is the only way it fits in 32 KB.
    • Kernel optimizations. I optimized every kernel in the model, which made decode more than 7× faster: 0.19 → 1.43 tokens/s.
    • No floating point. I removed every floating-point instruction from our kernels, so they run on integer math alone. That lets the hardware team leave the floating-point unit out of the chip and save the area.
    • Roofline analysis. The roofline analysis I did gave the hardware teams our memory bandwidth requirements: 100 MB/s from flash for the weights and 50 MB/s from PSRAM for the KV cache.
    • The reef-perf roofline visualizer. I built an online tool that shows our projected performance and bottlenecks from the latest performance-model runs. The model efficiency team can use it to try out different model architectures and estimate their performance, and the hardware teams can quickly see the effect of changing parameters.

    1. The problem: very little memory

    1.1 The workload

    The goal of an inference accelerator chip is to run an LLM. While we are looking at other workloads, our primary goal is inference.

    The challenging part is that our chip is tiny. We're a new club, and we don't have the funds (or the experience) yet to design an Nvidia GPU.

    So we decided to run a tiny model. It's called TinyStories-28M, from the TinyStories paper, a small GPT-Neo model. It can't code or do math, but it's enough to write coherent children's stories. It has 52 million parameters (3,000× fewer than GPT-3). Even so, it's extremely difficult to run.

    Our PD teams told us early on that we could support at most 40 KB of on-chip memory, of which 8 KB has to be saved for instructions.

    For reference, our model needs ~75 MB of space to store, and every token takes up 8 KB in the KV cache (1 KB for each of the 8 layers). This is where the challenge begins. The model and KV cache can't be stored on the chip, only a tiny portion can be worked on at any given time, and the rest has to be stored off-chip. This constraint is what drives the software choices we had to make.

    1.2 Why attention is hard

    For the linear layers in the model, we can stream the weights in. For example, calculating the query vector for a token is a single [1×512] × [512×512] (x · Wq) matmul. We can keep x in memory and continually stream [16×16] blocks of Wq from whatever external storage we have. The concern here is making sure we can stream the weights in fast enough.

    Attention, however, is difficult. The cornerstone of modern LLMs is the transformer, first introduced in the Attention Is All You Need paper from Google almost a decade ago. As the name suggests, the transformer relies on attention.

    Attention works by comparing a token to every token before it and calculating a score that says how much it "attends" to each of them. Turning those scores into weights uses a function called softmax, whose parameters require the entire input to calculate. That means we can't stream parts of the input through softmax: we need to see the entire input before calculating.

    2. The solution: flash attention

    Flash attention vs. standard attention

    Flash attention never stores the full set of scores. It walks through the keys and values one block at a time (16 positions here), so only one block has to be on-chip at once. To get the softmax right without seeing every score first, it uses a modification called online softmax and keeps three running values for each query: the largest score so far (m), the sum of exponentials so far (ℓ), and the weighted sum of values so far (O). When a new block arrives:

    1. Score the block against the query (a matmul) and find the block's largest score. The new running maximum is m′ = max(m, block max).
    2. If the maximum went up, everything accumulated so far was computed against the old m and is now too large by a factor of em′ − m. Multiply ℓ and O by α = em − m′ to correct them.
    3. Compute the block's probabilities p = es − m′, add their sum to ℓ, and add p · V (a second matmul) to O.

    After the last block, O / ℓ is exactly the attention output, the same as if every score had been stored. Each key and value is read once, and the only state that survives between blocks is m, ℓ and O. The working set is one block plus a few small running values no matter how long the context gets, and both steps that do the real work are matmuls on the matrix engine.

    attention.cc is my implementation. It streams each head's keys and values in 2 KB chunks and runs the loop above on every block. During decode there's only one query, so attend_row reads all 16 scores of a block as a single row and runs the softmax on that one vector.

    Implementing it with double buffering

    Loading a chunk and computing on it one after the other wastes time: the matrix engine waits while the DMA loads, and the DMA waits while the engine computes. With double buffering there are two buffers. While the engine computes on chunk i in one, the DMA loads chunk i+1 into the other. When both are done they swap. As long as computing a chunk takes about as long as loading one, the memory transfers are almost entirely hidden.

    3. Further optimizations I made to kernels

    To see what each optimization is worth, I added a switch for each one to the firmware and measured decode of token 200 on reef-perf, with weights streaming at 100 MB/s and the KV cache at 50 MB/s. I started with all of them off and turned them back on one at a time, from the smallest gain to the largest.

    The two biggest gains are both about memory. Storing the weights transposed, in the exact order the matrix engine reads them, turns each 2 KB chunk into one contiguous transfer. Without it, PyTorch's [out][in] layout splits every chunk into 64 separate 32-byte transfers, and the matrix engine has to gather its operands with strided loads. Double buffering then hides the load time behind compute. Decode is limited by how fast weights arrive, so these matter far more than making the compute itself faster. The int4 and low-rank bars are estimates: I applied the per-layer speedups we measured for those kernels (1.73× and 1.71×) to every linear layer, including the lm_head. Combining the two hasn't been run yet, so its bar assumes the speedups multiply.

    1. Transposed weights. Weights are stored offline in the order the matrix engine reads them, so every 2 KB chunk is one contiguous DMA and every operand load is contiguous. +400%, 0.29 → 1.45 tokens/s. On the RTL, one matrix engine step went from 84 to 25 cycles.
    2. Double buffering for the weights and the KV cache: the next chunk loads while the current one is computed. +43%, 0.20 → 0.29 tokens/s, measured before the transpose. Turning it off in today's firmware halves the speed (1.43 → 0.78 tokens/s).
    3. Linear layers on the matrix engine instead of the vector unit. +3% in the ladder; turning it off in today's firmware costs 12%.
    4. Lookup-table exp and precomputed GeLU. The integer-only vector unit made exp and GeLU's tanh expensive, so the softmax reads exp from a 256-entry table and GeLU is precomputed into its own 256-entry table indexed by the int8 input. +1.5% in the ladder; turning them off in today's firmware costs 8%.
    5. Fused epilogues. GeLU, the residual add and the lm_head's argmax happen inside the linear kernel instead of as separate passes, so the lm_head never stores its 50,257 scores. Turning it off in today's firmware costs 1%.
    6. Attention on the matrix engine, with decode reading each block's 16 scores as a single row. No decode gain at 200 tokens: attention is small at that length, and the vector unit keeps up. Without the row reads it's 11% slower than the vector unit.
    7. Integer-only LayerNorm, with 1/√variance in Q15 fixed point. About 2% slower than a float LayerNorm on a chip with an FPU, but it means the chip doesn't need one.
    8. Vectorizing every integer loop, with fixed-point requantization. Residual add 32×, LayerNorm 17×, GeLU 7.6×, MLP 6×, softmax 4× faster (RTL).
    9. Feature-major activations. Activations are stored as [feature][token], so a row is exactly what the matrix engine reads, and LayerNorm, softmax and requantization work across 16 tokens at once with plain vector instructions.
    10. KV cache in blocks of 16 positions, so each transfer is contiguous.

    With every optimization on, including the integer LayerNorm, decode runs at 1.43 tokens/s at token 200 and 1.30 tokens/s at 1,024 tokens of context (782 ms per token).

    4. Performance bottlenecks

    Memory rooflines

    With double buffering, each kernel computes on one 2 KB chunk while the next one loads. If computing a chunk takes 1,000 cycles, the next 2 KB has to arrive within 1,000 cycles, or the kernel waits on memory. So the time each kernel spends on one chunk sets the bandwidth it needs. For the linear layers a chunk is 2 KB of weights. For attention it's the keys and values of one head over 32 positions. These are measured on reef-perf with unlimited memory bandwidth, so they're compute time only.

    fc21,271 cycles81 MB/s
    lm_head1,201 cycles85 MB/s
    Attention (keys and values)2,424 cycles42 MB/s

    That's where our targets of 100 MB/s for the weights and 50 MB/s for the KV cache came from: every kernel needs less than that, so neither link holds it back. Past those rates more bandwidth stops helping, because the kernels can't consume data any faster. Sweeping the flash bandwidth shows it directly:

    Up to 100 MB/s, decode speed rises almost in step with bandwidth: it's memory bound. Past 100 MB/s it flattens at about 1.45 tokens/s, the speed with unlimited bandwidth, because now the core is the limit. The rest of this section is about why.

    Why the matrix engine is mostly idle

    During decode the matrix engine is busy about 1–2% of the time and gets nowhere near its peak ops/s. Part of that is physics. Decoding one token is a matrix-vector product, so each weight byte is used in exactly one MAC. At 100 MB/s flash delivers 2 bytes per cycle, which supports 2 MACs per cycle out of the engine's 128: a ceiling of 1.56% utilization, no matter what the core does. The same math gives the speed limit: 100 MB/s ÷ 52 MB per token ≈ 1.9 tokens/s.

    The other part is that we don't even reach that ceiling: even with 100 MB/s from flash to the DTCM, getting the weights from the DTCM into the matrix engine has a significant cost. Every weight byte takes this path:

    FlashDMA, 2 KB chunks DTCMload instruction, 16 B at a time Vector registerMAC instruction Matrix engine

    The core has to bring the weights from the DTCM into the matrix engine, and that's where we see the biggest performance bottleneck. It works like this. The matrix engine can't read memory on its own, so the core runs a load instruction for every 16 bytes of weights, which copies them from the DTCM into a vector register. Loads are executed by the core's load/store unit (LSU). The core can work on several instructions at once, and it tracks the ones in flight in a reorder buffer (ROB). Each instruction holds a ROB entry from when it's issued until it finishes, and when every entry is taken, the core can't issue anything new until one frees up.

    Each 2 KB chunk takes 128 vector loads through the LSU, at about 5 cycles each. Every load holds an entry in the 8-entry ROB until it finishes, and so does every MAC instruction, which keeps the engine busy for 8 cycles. With only 8 entries, a few loads and MACs fill the ROB quickly.

    We set our memory bandwidth at 100 MB/s because it takes about 1,200–1,450 cycles to compute on 2 KB of weights. If we look at what those cycles are doing, only a tiny fraction are matmuls; the rest is the core moving data around. Even though the matrix engine could consume data much faster than 100 MB/s, we're limited by how fast the core can feed it.

    Raising the flash bandwidth further shows the same thing from the other side. At 200 MB/s flash goes idle two thirds of the time, but the LSU stays exactly as busy, because it's now the limit.

    There are two different things we mean by matrix engine utilization. The first is time: what fraction of the workload's cycles the engine is doing anything at all. That's the busy share in the chart above, about 2% of decode at 100 MB/s. The second is how hard it works while it's running: when it is busy, how many of its 128 MACs per cycle it actually uses. Today each operation uses only 64 of the 128 slots, so even while it's busy the engine runs at half its peak. Multiply the two together and you get achieved ops/s compared to peak ops/s, which is what the next chart shows: about 1.2% at 100 MB/s.

    To see how much each limit costs, we removed them one at a time in the simulator. Unlimited bandwidth alone does almost nothing, because the core then caps it. Even with every memory-side limit gone, decode only reaches about 1.6%: the physics ceiling.

    Fixing the core takes two changes together. At 4 bytes/cycle of flash, a newer LSU (with overhead per instruction instead of per register) and a bigger ROB each help a little alone, but together they cut decode time by two thirds. A bigger ROB just fills with loads if the LSU is slow, and a faster LSU just fills the small ROB.

    Decode cycles per token, flash 4 B/cycleROB 8ROB 16
    Current LSU31.6M27.0M
    Newer LSU26.0M18.9M

    Batching moves the limit again. Decoding 8 stories in one pass over the weights uses each weight byte 8 times, so flash stops being the main limit. Then the core can't issue MAC instructions fast enough: it starts one about every 42 cycles, and each one holds a ROB entry for its 8 cycles of work. The ROB is full most of the time.

    So right now our biggest bottleneck is moving data around on the core. That isn't an inference problem, though, and our hardware teams are working hard on solving it.

    5. What we're working on

    Online roofline visualization

    Our kernel work had been all over the place, and I thought we needed a source of truth that every team could use to see what our performance on Coral looks like right now. So I built reef-perf-explorer.

    It shows our workflow as blocks, and for each block where the bottleneck is and how much that block contributes to our performance. You can see where our biggest bottlenecks are, overall and per system.

    When we talked to hardware, we had to build a separate explanation for everything, and a lot of the discussions were siloed (like the DMA discussion). Now there's one place where any number about our projected performance comes from, so anyone can track and understand it. The model efficiency team can try an architecture change, like more heads, a wider MLP or another TinyStories size, and hardware can try a change, like bandwidth, clock or DMA overlap. Both see right away how it moves our estimated performance and where the bottlenecks are, based on our most recent kernels.

    The first version used numbers from my RTL sims, since that's all we had. The team's feedback was that it should come straight from the performance model, so there wouldn't be four different models running around with no source of truth. Once the matrix engine was in reef-perf, I switched it to measured reef-perf runs for TinyStories-28M and 33M.

    Batching

    Decoding several stories in one pass over the weights uses each weight byte once per story, so we get more tokens out of the same bandwidth. The 32 KB DTCM caps us at 8 stories. In the simulator, with today's core and our target bandwidths, 8 stories together run at about 6.5 tokens/s, though each story on its own gets slower. As the dispatch-slot chart above shows, at batch 8 the limit moves from flash to how fast the core can issue MAC instructions.

    int4 quantization

    Storing the weights in int4 packs two weights into every byte, so each token streams half as many bytes. In decode the number of MACs equals the number of weights we load, and we're limited by how fast those weights arrive, so at the same bandwidth that roughly doubles tokens per second. In reef-perf, native int4 makes each layer's linear kernels 1.73× faster, which would take decode from 1.45 to about 2.35 tokens/s. We're working with the hardware teams on the best way to implement it. In our last meeting we decided to add int4 lanes to the Coral matrix engine spec (Coral has no native int4 support) while keeping int8 support in case we need it. On our end, the model efficiency team has confirmed that with quantization-aware training (QAT) we can quantize to int4 without a significant loss in output quality.

    Low-rank weights

    Instead of storing a full weight matrix, we store two thin ones that multiply to approximate it. A 16 × 16 matrix is 256 weights. Written as a 16 × 4 matrix times a 4 × 16 matrix, it's 128, half the bytes. For a d × d layer, rank d/4 halves the bytes. We apply the two thin matrices to the input one after the other, so the MACs shrink along with the bytes. In reef-perf it makes each layer's linear kernels 1.71× faster, about the same as int4, and the two can stack. We haven't checked accuracy for low-rank weights yet, but if it holds up, combining it with int4 could take decode to about 3.6 tokens/s, 2.5× today's speed. We haven't run that combination yet, so that number assumes the two speedups multiply.
